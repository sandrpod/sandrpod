# 工作区与角色

一个工作区拥有沙箱、成员、API 密钥、worker 和钱。一个账号可以属于多个工作区并随时
切换；任何东西都不跨工作区边界。

## 两种角色

| 动作 | owner | member |
|---|---|---|
| 创建、停止、删除沙箱 | ✓ | ✓ |
| 打开终端、执行代码、移动文件 | ✓ | ✓ |
| 查看用量、审计、设置 | ✓ | ✓ |
| 邀请或移除成员 | ✓ | ✗ |
| 创建或吊销 API 密钥 | ✓ | ✗ |
| 充值、改套餐、删除工作区 | ✓ | ✗ |
| 签发 worker join token | ✓ | ✗ |

member 是协作者，不是共有者。这条区分在服务端执行 —— member 调 owner 专属接口会拿到
`403 owner_required`，而不是一个被藏起来的按钮。

**为什么只有两种角色。** 每多一种角色，邀请时就得有人做一次判断，而实际场景无非是
"用沙箱的人"和"付钱的人"。团队需要更细的控制，就给每组开一个工作区 —— 边界本来就在
那里，加一个不多花任何代价。

## 邀请

**设置 → 成员 → 邀请** 会发出一个链接。对方要么用它注册（邀请制部署），要么用它加入已有
账号。注册模式是部署级设置：

| 模式 | 谁能创建账号 |
|---|---|
| `open` | 拿到地址的人 |
| `invite` | 只能通过邀请 |
| `closed` | 谁都不行；由管理员建号 |

## 删除

| 删什么 | 效果 |
|---|---|
| 一个沙箱 | 容器和记录消失；已经计量的用量照旧计量 |
| 一个工作区 | 沙箱、密钥、成员、审计、join token 一并删除；支付记录为税务保留，但与工作区脱钩 |
| 一个账号 | 同工作区，外加会话和验证 token |

删除立即生效且记录在案。没有"回收站"可以反悔 —— 需要数据就先导出或做快照。

## 审计

工作区能看到的每个生命周期事件都落在 **审计** 里：谁创建了什么、什么时候启动、什么时候
删除、占用了多少资源。保留 **180 天**，之后清理 —— 这是有清理器兜底的承诺。
